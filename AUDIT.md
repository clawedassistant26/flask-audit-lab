# Security Audit: Expense Tracker API

**Target:** `vulnerable/app.py` (Flask + SQLite expense tracker, 9 endpoints)
**Reviewer:** Clawed Assistant
**Date:** 27/07/2026
**Method:** Manual line by line code review, mapped to the OWASP Top 10 (2021), with a working exploit written for every finding before it was reported.
**Scope:** Application code only. No infrastructure, TLS, dependency or deployment review.

---

## 1. Summary

Nine vulnerabilities were found. Three are critical: any authenticated user can read and modify every other user's data, and the session token can be regenerated by an attacker who never sees it.

The core problem is that the application trusts the caller. User input reaches SQL as text, request bodies are written straight into database columns, and object ownership is never checked. Any one of these alone would be serious. Together they mean a single registered account is enough to read the whole database.

All nine findings are closed in `hardened/app.py`. Both builds expose the same API and pass the same 18 parity tests, so the fixes do not change how a legitimate client uses the service.

| ID | Finding | OWASP | Severity |
|----|---------|-------|----------|
| F-01 | SQL injection in expense search | A03 Injection | Critical |
| F-02 | IDOR: any expense readable by id | A01 Broken Access Control | Critical |
| F-04 | Session token derived from public data | A07 Auth Failures | Critical |
| F-03 | Unsalted MD5 password storage | A02 Cryptographic Failures | High |
| F-07 | Mass assignment on expense creation | A08 Data Integrity Failures | High |
| F-06 | No login rate limiting | A04 Insecure Design | Medium |
| F-05 | Traceback disclosure and debug mode | A05 Misconfiguration | Medium |
| F-08 | Session token written to logs | A09 Logging Failures | Medium |
| F-09 | Username enumeration on login | A07 Auth Failures | Low |

**Severity** reflects impact on this application assuming an internet facing deployment with untrusted registered users. CVSS v3.1 base vectors are given per finding. Base scores ignore environment, so treat them as a ranking aid and not a final risk number.

## 2. Findings

### F-01 SQL injection in expense search
**OWASP:** A03 Injection · **Severity:** Critical · **CVSS:** 8.1 (`AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:N`)
**Location:** `vulnerable/app.py:180`

The `q` parameter is formatted into the SQL string with an f-string:

```python
sql = (
    "SELECT * FROM expenses WHERE user_id = "
    f"{user['id']} AND description LIKE '%{q}%'"
)
```

The caller controls the text of the `WHERE` clause, so they can close the `LIKE` pattern and append their own logic.

**Proof of concept.** `test_f01_injection_leaks_other_users_rows_on_vulnerable` sends `q=%' OR '1'='1' --` as an authenticated attacker who owns no expenses. The server builds:

```sql
SELECT * FROM expenses WHERE user_id = 2 AND description LIKE '%%' OR '1'='1' --%'
```

The `--` comments out the trailing quote, leaving a condition that is true for every row. The attacker receives the victim's expenses.

**Impact.** Full read access to the `expenses` table. SQLite allows `UNION SELECT` against other tables through the same hole, so `users` and `sessions` are reachable too, which turns this into credential and live session theft. This is the most serious finding in the report.

**Remediation.** Bind the value as a parameter and never build SQL by concatenation. Escape LIKE wildcards separately, because parameterisation stops injection but still lets a caller pass `%` and widen their own match:

```python
escaped = q.replace("\\", "\\\\").replace("%", "\\%").replace("_", "\\_")
rows = db().execute(
    "SELECT * FROM expenses WHERE user_id = ? AND description LIKE ? ESCAPE '\\'",
    (user["id"], f"%{escaped}%"),
).fetchall()
```

**Verification.** The same payload against the hardened build returns `[]`. `test_f01_hardened_still_matches_a_literal_percent` confirms searching for `50%` still finds "50% deposit", so the escaping did not break real searches.

### F-02 Any expense is readable by id
**OWASP:** A01 Broken Access Control · **Severity:** Critical · **CVSS:** 6.5 (`AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:N/A:N`)
**Location:** `vulnerable/app.py:166`

`GET /expenses/<id>` authenticates the caller but never checks that the row belongs to them:

```python
row = db().execute("SELECT * FROM expenses WHERE id = ?", (expense_id,)).fetchone()
```

**Proof of concept.** `test_f02_idor_reads_another_users_expense_on_vulnerable` logs in as the attacker and requests `/expenses/1`, which belongs to the victim. It returns 200 with the victim's data.

**Impact.** Expense ids are sequential integers, so an attacker can walk the whole table with a loop. Authentication without authorisation is the single most common flaw in this class of application.

**Remediation.** Make ownership part of the query rather than a separate check, so there is no path that forgets it:

```python
row = db().execute(
    "SELECT * FROM expenses WHERE id = ? AND user_id = ?",
    (expense_id, user["id"]),
).fetchone()
```

Return 404 rather than 403 for a row the caller does not own. A 403 confirms the id exists, which leaks the size and shape of the table.

**Verification.** The attacker now gets 404. `test_f02_owner_can_still_read_their_own_expense` confirms the owner is unaffected.

### F-04 Session token is derived from public data
**OWASP:** A07 Identification and Authentication Failures · **Severity:** Critical · **CVSS:** 8.1 (`AV:N/AC:H/PR:N/UI:N/S:U/C:H/I:H/A:H`)
**Location:** `vulnerable/app.py:73`

```python
def issue_token(username):
    return hashlib.md5(f"{username}{int(time.time())}".encode()).hexdigest()
```

Both inputs are known or guessable. The username is public and the login time is a single unix second. The token holds no secret at all.

**Proof of concept.** `test_f04_token_is_predictable_on_vulnerable` never reads the victim's token. It takes the username and an approximate login time, computes the MD5 for each second in a 11 second window, and tries each against `/expenses`. One works, and it matches the real token exactly.

**Impact.** Full account takeover without touching the victim's password or network traffic. A real attacker who knows only the username can widen the window to hours and still finish in seconds. Tokens are also stored in plaintext and never expire, so a database read hands over permanent live sessions.

**Remediation.** Take the token from the CSPRNG, so it is unrelated to any public value. Store only its hash, and give it an expiry:

```python
token = secrets.token_urlsafe(32)
db().execute(
    "INSERT OR REPLACE INTO sessions (token_hash, user_id, expires_at) VALUES (?, ?, ?)",
    (hashlib.sha256(token.encode()).hexdigest(), user_id, int(time.time()) + 3600),
)
```

**Verification.** Four tests. The brute force finds nothing; five logins produce five distinct tokens; the sessions table contains the SHA-256 and not the token; and a token stops working once the TTL passes.

### F-03 Passwords stored as unsalted MD5
**OWASP:** A02 Cryptographic Failures · **Severity:** High · **CVSS:** 7.5 (`AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:N/A:N`)
**Location:** `vulnerable/app.py:67`

```python
def hash_password(password):
    return hashlib.md5(password.encode()).hexdigest()
```

MD5 is fast by design, which is the opposite of what password storage needs, and there is no salt.

**Proof of concept.** `test_f03_vulnerable_hash_falls_to_a_precomputed_lookup` reads the hash straight from the database and recovers the password with a plain dictionary lookup, one MD5 per candidate and no per-user work. `test_f03_identical_passwords_collide_on_vulnerable` shows two users with the same password get the same hash, so an attacker can group accounts by shared password before cracking anything.

**Impact.** This finding only pays off once an attacker already has the database, but F-01 gives them that. Password reuse then turns one breach into compromise of the same users elsewhere.

**Remediation.** Use a memory hard KDF with a per-user random salt. `hashlib.scrypt` is in the standard library, so this needs no new dependency:

```python
salt = os.urandom(16)
digest = hashlib.scrypt(password.encode(), salt=salt, n=2**14, r=8, p=1, dklen=32)
return f"scrypt${n}${r}${p}${salt.hex()}${digest.hex()}"
```

Storing the parameters alongside the hash means the work factor can be raised later without invalidating existing hashes. Compare with `hmac.compare_digest`, not `==`.

**Verification.** The dictionary attack fails, and two users with the same password now get different hashes.

### F-07 Mass assignment on expense creation
**OWASP:** A08 Software and Data Integrity Failures · **Severity:** High · **CVSS:** 8.1 (`AV:N/AC:L/PR:L/UI:N/S:U/C:N/I:H/A:H`)
**Location:** `vulnerable/app.py:149`

Every key in the request body becomes a column name:

```python
columns = ", ".join(payload.keys())
placeholders = ", ".join("?" for _ in payload)
cur = db().execute(f"INSERT INTO expenses ({columns}) VALUES ({placeholders})", ...)
```

**Proof of concept.** `test_f07_client_can_self_approve_and_reassign_on_vulnerable` posts an expense with `is_approved: 1` and `user_id: 1`. Both are written. The attacker has approved their own 5000.00 expense and booked it against the victim.

**Impact.** This is the finding with real money attached. It defeats the approval workflow the application exists to enforce. Column names also come from the request, so a bad key produces a SQL error, which combined with F-05 leaks the schema.

**Remediation.** Read named fields explicitly and validate their types. Never iterate over client keys:

```python
description = payload.get("description")
amount_cents = payload.get("amount_cents")
if not isinstance(amount_cents, int) or isinstance(amount_cents, bool):
    return jsonify({"error": "amount_cents must be an integer"}), 400
```

`user_id` comes from the session, and `is_approved` keeps its database default. The `bool` check matters because `isinstance(True, int)` is true in Python, so `True` would otherwise pass as an amount.

**Verification.** The same request now stores the attacker's own id with `is_approved = 0`, and malformed amounts are rejected with 400.

### F-06 No rate limiting on login
**OWASP:** A04 Insecure Design · **Severity:** Medium · **CVSS:** 5.3 (`AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:N/A:N`)
**Location:** `vulnerable/app.py:106`

There is no lockout, delay or counter. Guesses run as fast as the network allows.

**Proof of concept.** `test_f06_vulnerable_never_throttles` makes 50 failed attempts against one account. Every response is 401. Nothing slows down and nothing locks.

**Impact.** Credential stuffing against a known username list is unconstrained. Because F-03 makes weak passwords likely to survive, this is a realistic path in.

**Remediation.** Count failures per username in a fixed window and return 429 past the threshold. In production, put this in shared storage such as Redis rather than process memory, and key on client IP as well as username so one attacker cannot lock every account out on purpose. The in-process version here is deliberately simple, and that limitation is called out in the README rather than hidden.

**Verification.** Three tests: the sixth attempt returns 429; a correct password during lockout still returns 429 and no token; and a successful login clears the counter so a legitimate user who mistyped is not punished.

### F-05 Traceback disclosure and debug mode
**OWASP:** A05 Security Misconfiguration · **Severity:** Medium · **CVSS:** 5.3 (`AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:N/A:N`)
**Location:** `vulnerable/app.py:208` and `vulnerable/app.py:218`

The error handler returns the exception text and full traceback to the client. The entrypoint also runs with `debug=True`.

**Proof of concept.** `test_f05_vulnerable_leaks_a_traceback` requests `/rates?divisor=0` and gets a 500 whose body contains the traceback and server file paths.

**Impact.** Tracebacks give an attacker file paths, library versions and code structure, which makes every other finding easier to exploit. `debug=True` is worse: the Werkzeug debugger is remote code execution if it is ever reachable, and "temporarily" enabling it in production is a common mistake.

**Remediation.** Log the detail server side, return an opaque message, and never ship `debug=True`:

```python
@app.errorhandler(Exception)
def handle_error(exc):
    LOG.exception("unhandled error: %s", exc)
    return jsonify({"error": "internal server error"}), 500
```

Validate input so expected failures return 400 rather than reaching the handler at all.

**Verification.** `/rates?divisor=0` now returns a validated 400 with no traceback. A separate test registers a route that raises an unexpected error and confirms the message stays server side.

### F-08 Session token written to the log
**OWASP:** A09 Security Logging and Monitoring Failures · **Severity:** Medium · **CVSS:** 5.5 (`AV:L/AC:L/PR:L/UI:N/S:U/C:H/I:N/A:N`)
**Location:** `vulnerable/app.py:126`

```python
LOG.info("login ok user=%s token=%s", username, token)
```

**Proof of concept.** `test_f08_vulnerable_logs_the_bearer_token` captures log output during login and finds the exact token in it.

**Impact.** Logs are copied to aggregators, backups and support tickets, and are usually readable by more people than the database is. Anyone with log access can replay a live session. Since F-04 tokens never expire, that access is permanent.

**Remediation.** Log the user id, not the credential. The event stays auditable and the secret does not leave the auth path:

```python
LOG.info("login ok user_id=%s", row["id"])
```

The same rule applies to passwords, API keys and full card numbers. If correlating a specific session is genuinely needed, log a hash prefix instead of the token.

**Verification.** The token no longer appears in captured output, and the test still asserts the login event is recorded, so the fix did not blind the audit trail.

### F-09 Username enumeration on login
**OWASP:** A07 Identification and Authentication Failures · **Severity:** Low · **CVSS:** 3.7 (`AV:N/AC:H/PR:N/UI:N/S:U/C:L/I:N/A:N`)
**Location:** `vulnerable/app.py:115` and `vulnerable/app.py:117`

An unknown user returns 404 "no such user" and a wrong password returns 401 "wrong password".

**Proof of concept.** `test_f09_vulnerable_reveals_which_usernames_exist` sends the same wrong password to a real account and a fake one, and gets two different status codes.

**Impact.** An attacker can confirm which accounts exist before spending any effort guessing passwords, which makes F-06 considerably more efficient. Low on its own, and it matters because of what it feeds.

**Remediation.** Return one response for both cases, and do the same work in both paths so response time does not leak what the status code no longer does:

```python
if row is None:
    verify_password(password, hash_password("decoy-password"))
    return jsonify({"error": "invalid credentials"}), 401
```

Without that decoy hash, the unknown user path returns immediately while the real path spends time in scrypt, and the timing difference restores the leak.

**Verification.** Both cases now return an identical 401 status and body.

## 3. What was checked and found clean

Stating what was reviewed and found sound matters as much as the findings, so the client knows the boundary of the work.

- **Authentication on protected routes.** All five protected endpoints reject missing and malformed tokens. Verified in `test_expenses_require_authentication`.
- **The admin role check** on `/admin/report` is correct in both builds. A normal user gets 403.
- **Registration** rejects empty usernames and passwords, and duplicate usernames return 409 rather than overwriting an account.
- **Parameterised queries elsewhere.** `search_expenses` was the only endpoint building SQL by concatenation. Login, registration and expense listing already bound their parameters.

## 4. Limitations

- Application code only. No review of TLS, hosting, CORS, dependency versions or secrets management.
- Not tested: concurrency and race conditions, denial of service under load, or anything requiring a running deployment rather than the test client.
- CVSS base scores assume an internet facing deployment with untrusted registered users. A different deployment changes them.
- The lockout in F-06 is in process memory, so it resets on restart and does not work across multiple workers. Production needs shared storage. This is a known limitation of the fix as written, not an oversight.
- No authenticated third party scanner was run. Findings come from manual review, and each one is backed by a working exploit rather than a tool's confidence rating.

## 5. Reproducing this audit

```bash
pip install -r requirements.txt
pytest tests/ -v
```

95 tests, in three groups:

- **31 exploit tests** fire each attack at both builds and assert it works against `vulnerable/` and fails against `hardened/`.
- **18 parity tests**, each run against both builds, run the same legitimate workflows and assert identical behaviour. These are what show the fixes did not break the product.
- **Contract tests** check `openapi.yaml` against the hardened build, so the documentation cannot drift from the code without the build going red.
